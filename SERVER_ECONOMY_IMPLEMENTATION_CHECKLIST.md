# Pelmeni Clicker — чек-лист подготовки серверной экономики

**Статус (2026-11-03):** подготовительный документ. Клиентские правила обновлены; локальная SQL-миграция подготовлена, но не применена. Текущая `sync-game` обслуживает только `load` и полный `save`, не маршрутизирует новые экономические RPC. Серверная экономика не активна. Supabase Dashboard в рамках этой проверки не открывался.

## 1. Что подтверждено локально

- В `app.js` клиент вызывает `load` с исходной строкой `Telegram.WebApp.initData` из `initializeState()` и вызывает `save` из `flushCloudSave()`. `save` отправляет полный сериализованный снимок состояния.
- `saveState()` сначала пишет локальную копию, затем запускает облачное сохранение с debounce 650 мс. При проблеме с сетью клиент может продолжить локально. Такой снимок нельзя принимать за подтверждённую сервером экономическую операцию.
- `normalizeState()` поддерживает legacy-поля и преобразования старых сохранений; активные партии сериализуются в составе полного состояния. Локальный импорт зависит от локальных ключей и не доказывает Telegram-владение.
- `game-rules.js` и `tests/game-rules.test.cjs` находятся локально. Тесты охватывают формулы правил, но не Edge Function, SQL, RLS, конкурентные транзакции, миграцию или совместимость старых вкладок.
- Локально есть исходник `supabase/functions/sync-game/index.ts` и подготовленная миграция `supabase/migrations/20261029000000_server_economy.sql`; это не подтверждает, что та же версия опубликована или что миграция применена. Контракт существующей функции (`load`/`save`, проверка `initData`) ранее описан владельцем проекта, но его текущая опубликованная версия здесь не проверялась.
- В предыдущем описании проекта назывались столбцы `telegram_id`, `game_state`, `updated_at`. Это не подтверждение текущей схемы Dashboard: до её получения считать фактические типы, ограничения, политики и права неизвестными.

## 2. Пакет сведений из Supabase Dashboard

Перед любым проектированием миграции соберите сведения в текстовом документе. Не присылайте строки таблицы, данные игроков, Telegram `initData`, заголовки авторизации, значения Secrets или ключи.

### A. Таблица и ограничения

1. Откройте **Database → Table Editor → `public.player_state` → Definition/Structure** (название вкладки может отличаться).
2. Скопируйте только список столбцов: имя, тип, nullable, default, identity/generated; первичный и внешние ключи; `CHECK`, `UNIQUE` и другие ограничения. Также укажите, существует ли таблица и точное имя схемы/таблицы.
3. Не копируйте строки таблицы и не прикладывайте экспорт игровых профилей.

**Нужно подтвердить:** существует ли таблица; точные типы JSON/ID/дат; допускаются ли отсутствующие значения; какие ограничения могут блокировать новые поля или транзакционные операции.

### B. RLS и права таблицы

1. Откройте **Database → Table Editor → `player_state` → Policies** или **Authentication/Database → Policies**.
2. Укажите, включён ли RLS. Для каждой политики скопируйте имя, команду (`SELECT`/`INSERT`/`UPDATE`/`DELETE`/`ALL`), роли, `USING` и `WITH CHECK`.
3. Найдите экран **Privileges/Grants** для таблицы и передайте только матрицу ролей и разрешений (например, роль → SELECT/INSERT/UPDATE/DELETE: разрешено/запрещено). Не копируйте ключи или учётные данные ролей.

**Нужно подтвердить:** может ли публичная роль обращаться к таблице напрямую и от чьего имени выполняются запросы функции. Не включайте в ответ SQL/логи с токенами или персональными данными.

### C. Индексы, триггеры и связанные функции БД

1. В **Database → Table Editor → `player_state` → Indexes/Constraints** скопируйте для каждого индекса его имя, уникальность, столбцы/выражение и условие partial index, если есть.
2. В **Database → Triggers** найдите триггеры на этой таблице. Скопируйте имя, событие, момент выполнения и вызываемую функцию.
3. В **Database → Functions** найдите функции, которые вызываются этими триггерами или функцией `quick-function`; передайте сигнатуру и тело только относящихся к игровому сохранению функций.
4. Если Dashboard показывает полный SQL определения объекта, перед отправкой просмотрите его и замените любые значения секретов/конфигурации на `[REDACTED]`.

**Нужно подтвердить:** есть ли уже уникальность, автоматические изменения `updated_at`, побочные эффекты или функции, конфликтующие с будущими транзакциями.

### D. Опубликованная Edge Function

1. Откройте **Edge Functions → `quick-function` → Code/Details**.
2. Скопируйте весь исходный код всех файлов функции, включая импортируемые локальные модули, если Dashboard их показывает. Сохраните имена файлов и пути. Если редактор показывает только точку входа, отметьте это отдельно.
3. На странице настроек/деталей функции передайте только несекретные настройки: включена ли проверка JWT платформы, текущий статус/версию или время последнего deploy, если они отображаются, и список имён используемых переменных окружения без значений.
4. **Не открывайте и не копируйте значения** из **Secrets/Environment Variables**. Не присылайте bot token, `service_role`, приватные ключи, Telegram `initData`, заголовки `Authorization` или любые секреты. Удалите подобные строки из кода, если они оказались встроены в исходник; вместо значения оставьте `[REDACTED]` и укажите имя переменной.
5. Не присылайте сырые логи запросов. Если для понимания ошибки понадобится пример, скопируйте только сообщение/код ошибки и тип операции, предварительно удалив Telegram ID, имена, баланс, `game_state`, initData и заголовки.

**Нужно подтвердить:** действительный код авторизации и проверки подписи/срока `initData`, парсинг тела, DB-вызовы, обработку ошибок, использование секретов и то, принимает ли текущая функция произвольное полное состояние.

### E. Данные профилей — не выгружать в чат

Для безопасной совместимости нужно знать разнообразие сохранений, но присылать реальные записи не надо. Позже снимите резервную копию в защищённом месте и анализируйте её локально/в изолированной тестовой копии. Пока можно сообщить только агрегаты: число записей, диапазоны версий состояния, количество записей с `activeBatches`, старым одиночным таймером, `points`/`pointsRetired`, без ID и значений баланса. Если Dashboard не умеет агрегировать без выдачи строк, этот пункт отложить до подготовки безопасной копии.

## 3. Этапы будущего внедрения и контрольные ворота

Ниже последовательность, а не разрешение выполнять изменения сейчас. Каждый этап начинается только после прохождения предыдущих проверок.

### Этап 0 — зафиксировать текущий контракт и получить схему

**Действия:** сохранить этот чек-лист и план; получить пакет A–D; сверить с текущим клиентом `load`/`save`; составить карту версий и полей `game_state` на обезличенной копии.

**Проверки перед переходом:** код функции целиком доступен; известны фактические колонки, ограничения, индексы, политики, grants, триггеры и вызываемые функции; секреты удалены.

**Успех:** все зависимости текущего `save` и авторизации прослеживаются от HTTP до записи в БД, неизвестные места явно перечислены.

**Остановиться, если:** исходник функции неполон, неизвестно, от чьего имени она обращается к БД, Dashboard-конфигурация противоречит коду или неясно, какие данные/таблицы изменяются.

### Этап 1 — резервная копия и восстановление

**Действия:** до любых изменений сделать резервную копию БД предусмотренным текущим тарифом/настройкой Supabase способом. Зафиксировать время, проект и охват копии. Проверить восстановление в отдельном тестовом проекте/окружении, не поверх production. Отдельно сохранить версию опубликованной функции и текущего клиентского релиза.

**Проверки перед переходом:** понять, входят ли в backup нужные таблицы, функции, триггеры и настройки; проверить, что копия доступна и может быть восстановлена; не хранить секреты рядом с экспортом.

**Успех:** есть защищённая копия и подтверждённый способ восстановления, а тестовое окружение изолировано от реальных игроков.

**Остановиться, если:** backup неполный, восстановление не проверено, тесты могут затронуть production-профили или невозможно точно определить окно данных для отката.

### Этап 2 — целевая транзакционная реализация на тестовой копии

**Действия:** реализовать серверные операции по утверждённому `SERVER_ECONOMY_PLAN.md`. Каждая экономическая команда в одной транзакции проверяет игрока/условия, изменяет состояние и записывает idempotency receipt. Повтор того же `requestId` с теми же параметрами возвращает прежний результат; тот же ID с иными параметрами отклоняется. Параллельные запросы сериализуются блокировкой профиля/уникальными ограничениями. Проверить фактическую поддержку транзакций с текущей схемой и способом вызова из Edge Function.

**Проверки перед переходом:** сравнить серверные вычисления с текущими `game-rules.js` и тестами; добавить серверные unit/integration тесты на конкурентность, повтор, двойной сбор, недостаточный баланс и неверные входные данные; проверить RLS и полномочия DB-вызова на тестовой копии.

**Успех:** автоматические тесты доказывают единственное начисление и атомарный отказ без частичного списания; у каждого успешного изменения есть однозначный receipt; существующая схема не потеряла записи.

**Остановиться, если:** операция опирается на переданную клиентом цену/награду/таймер; проверка и изменение разделены разными нетранзакционными запросами; повтор или гонка дают двойное начисление; тесты используют реальные профили.

### Этап 3 — однократная миграция старых профилей

**Действия:** сохранить весь существующий профиль и неэкономические поля. Для каждого профиля присвоить однократную отметку версии импорта, которая запрещает повторное применение. Существующий серверный снимок переносить без повторного начисления; старый баланс, счёт и покупки сохранить как legacy opening state, не выдавая их за исторически проверенные. Импортировать старые клиентские данные только если сервер после успешного `load` подтвердил отсутствие профиля и нет неоднозначного локального legacy-источника.

Старые `startedAt`/`endsAt` не доказывают готовность партии. Не выдавать награду по старому таймеру. Сохранить подтверждённый занятый слот/состояние ожидания и назначить безопасный новый серверный срок по действующим правилам; если запись конфликтует или невалидна — помещать её в отчёт ручной обработки, не удалять и не начислять автоматически.

**Проверки перед переходом:** dry-run только на копии; посчитать до/после число профилей и агрегаты баланса/счёта/уровней/покупок/claims/партий; проверить версии и поля; повторный запуск миграции не меняет ни одну запись.

**Успех:** число обработанных профилей сходится; баланс, очки, приобретённые предметы и прогресс не теряются при преобразовании; не появляется повторных выплат; все аномалии вынесены отдельно.

**Остановиться, если:** профиль исчезает/обнуляется, агрегаты не сходятся без объяснения, конверсия legacy-полей применяется повторно, миграция создаёт награду из старого клиентского timestamp либо неясно, кому принадлежит локальный legacy-снимок.

### Этап 4 — постепенное обновление клиента при сохранённом старом контракте

**Действия:** выпустить клиент, который проверяет версию/возможности API и использует серверные команды для экономических операций; локальное хранилище оставить кэшем отображения/восстановления интерфейса, не источником серверных начислений. В переходном периоде Edge Function может обслуживать старые и новые протоколы, но старый `save` не должен иметь возможности перезаписать профиль после его серверной канонизации.

**Проверки перед переходом:** на тестовом профиле пройти загрузку, старт/сбор, покупки и claims; сверить возвращённое сервером состояние; эмулировать потерю ответа и повторить тот же `requestId`; проверить, что новый клиент не делает fallback на полный `save` при неизвестном действии/ошибке версии.

**Успех:** новая вкладка после перезапуска показывает серверное состояние; повтор команды не повторяет эффект; клиент чётко показывает требование обновиться и не считает локальную копию подтверждённой.

**Остановиться, если:** новый клиент при несовместимости отправляет старый полный снимок, облачный отказ незаметно превращается в локально подтверждённую экономику, либо новые и старые записи могут перезаписать друг друга.

### Этап 5 — тестовый профиль и совместимость открытых старых вкладок

**Действия:** выполнять сценарии на отдельном тестовом Telegram-профиле/окружении. Проверить две вкладки с одним профилем и одну вкладку со старым кодом. Старый клиент не знает нового протокола и может сохранить изменения только локально после отказа сервера; поэтому до переключения требуется явное уведомление о перезагрузке/обновлении, а сервер после канонизации должен отказать старому полному `save`, а не принимать его как восстановление.

**Проверки:** два одинаковых запроса одновременно; одинаковый `requestId` повторно; тот же ID с изменёнными параметрами; две разные команды при ограниченном балансе; две попытки собрать одну партию; старая вкладка после нового сохранения; отключение сети и возврат сети; восстановление страницы во время активной партии.

**Успех:** нет двойного начисления/списания; старая вкладка не затирает серверное состояние; новый клиент не трактует отказ как успешное сохранение; поведение при восстановлении соответствует согласованной политике.

**Остановиться, если:** старая вкладка может записать устаревший полный снимок, новая вкладка автоматически сливает недоверенные локальные изменения или тесты затронули не тестовый профиль.

### Этап 6 — переключение и откат

**Критерии переключения:** backup восстановим; схема/политики/права подтверждены; серверные транзакции и тесты гонок проходят; dry-run импорта сходится; тестовый профиль прошёл сценарии, включая старую вкладку; есть наблюдаемость по версиям клиента, отказам, идемпотентным повторам и ошибкам без записи секретов/персональных данных; подготовлена инструкция уведомления о перезагрузке.

**Порядок:** переключать поэтапно или по тестовой когорте; канонизацию и отказ полного `save` выполнять атомарно на уровне профиля/серверного режима. `save` сначала сохранять как совместимый маршрут, который для уже канонического профиля возвращает явный отказ `client_outdated`/аналогичный код, а не меняет состояние. После завершения переходного периода отдельным релизом удалить старый маршрут. Не выключать `save` глобально до проверки клиентов, которые ещё его используют.

**Условия остановки/отката:** любое расхождение состояния, потеря профиля, повторная награда, сбой транзакций, неожиданный рост отказов или возможность старой записи затереть новое состояние. Сначала остановить дальнейшее расширение переключения и перевести новые изменения в безопасный режим без записи (например, read-only/сообщение об ошибке). Не включать обратно произвольный `save` поверх профилей, уже записанных серверными операциями.

**Безопасный откат:** предпочитать исправление вперёд. Если откат к предыдущему клиенту необходим, старые профили не должны вновь принимать произвольный полный `game_state`. Восстановление из backup допустимо только по заранее проверенному сценарию с учётом всех законных операций после точки копии; не восстанавливать старую копию поверх свежих игровых изменений без сверки/журнала операций. Нельзя обещать отсутствие потери данных до фактической проверки такого сценария.

## 4. Риски, которые остаются до проверки Dashboard

- Неизвестны реальная структура таблиц, типы, defaults, ограничения, индексы и связи; целевая модель может конфликтовать с текущими объектами.
- Неизвестны RLS, table grants и фактическая DB-роль Edge Function; нельзя оценить риск прямой записи клиентом или выбрать безопасный механизм транзакции.
- Без полного кода опубликованной функции нельзя проверить авторизацию `initData`, возраст/повторность, обработку ошибок и то, какие таблицы/функции она меняет.
- Неизвестны триггеры, фоновые функции и ограничения/политики, которые могут менять или блокировать профиль.
- Сохранения и локальные копии могут быть подделаны исторически. Их перенос сохраняет данные как legacy-снимок, но не доказывает происхождение баланса/покупок.
- Старые открытые вкладки не передают версию профиля или `requestId`; их несинхронизированные локальные изменения нельзя безопасно автоматически объединить с серверной экономикой.
- Старые таймеры не доказывают окончание партии. Безопасный импорт может потребовать нового серверного ожидания для занятой кастрюли.
- Пока не проверено восстановление backup, нельзя утверждать, что откат не потеряет изменения после момента создания копии.

## 5. Следующий безопасный шаг

Сначала пришлите очищенный от секретов пакет из разделов **2A–2D**: структуру таблицы и её ограничения, состояние RLS/политик и матрицу grants, индексы/триггеры/связанные DB-функции, полный исходник всех файлов `quick-function` и только несекретные настройки функции. Не присылайте данные игроков или значения секретов. До этого не начинать SQL, миграцию или деплой.
