## 2. Idempotency and concurrency

| Scenario | Action | Expected result |
|---|---|---|
| Same request repeated | Call one operation twice with the same player, `requestId`, action, and parameters | One state mutation; second call returns the saved operation result and current canonical state/revision. |
| Conflicting request ID | Reuse a prior `requestId` with a different action or parameters | `idempotency_conflict`; no new mutation and no replacement of the original receipt. |
| Parallel exact retry | Send the same request concurrently | One applied result; the other sees the receipt after the profile-row lock; one increment/reward total. |
| Parallel distinct collection requests | Two request IDs collect the same ready `batchId` | At most one collection and one reward; the second sees the batch absent/already handled and changes no economic field. |
| Parallel purchases at boundary balance | Two different purchase requests whose combined prices exceed balance | Serialized decisions; balance never becomes negative and no partial purchase occurs. |
| Retry after UTC midnight | Repeat an already recorded request after the UTC day changes | Return the stored outcome and current canonical state/revision; do not apply it again. |
| Stale daily state | Send a new command after midnight before `economy_load_visit` has rolled the profile forward | Return `daily_state_stale` without mutation, revision increment, or request receipt; after `load_visit`, a new attempt may proceed against today's tasks. |
| Repeated equip no-op | Request equip/remove when the decoration already has that state, using a new request ID | Record the request outcome for idempotency, but leave `game_state`, `revision`, and `player_state.updated_at` unchanged. Exact retry returns that recorded outcome. |
| Collect either pot while the other is active | Create two distinct active batches, collect one ready batch, then inspect `activeBatches`, `startedAt`, `endsAt`, and `batchDurationMs` | The collected batch is removed. The single-batch compatibility fields match the remaining primary batch (pot 1 first, otherwise pot 2). The other batch retains its original id, pot, start/end time, and duration and remains collectible. Repeat with the other pot as the collected batch. |
| Collect the final active batch | Collect the only ready batch | `activeBatches` is empty and `startedAt`, `endsAt`, and `batchDurationMs` are JSON null; no stale timer remains in the compatibility fields. |

Also inspect `player_economy_requests`: one `(telegram_id, request_id)` row per accepted request key, stable action/parameters/outcome, and no Telegram `initData` stored there.

## 4. Atomic rollback on internal failure

In the disposable database only, add a temporary `BEFORE UPDATE` trigger on `player_economy_control` that raises for the synthetic profile. Each operation updates `player_state` first and `player_economy_control` second, so this injects the failure after the state write has executed. Call a purchase, collection, task claim, and `load/visit` separately. For command operations, assert that all of the following roll back together; for `load/visit`, check the state and revision (that RPC has no request receipt):

- `player_state.game_state` and `updated_at`;
- `player_economy_control.revision`;
- for commands, the idempotency request row.

Remove the temporary failure trigger and retry the command with the same request ID. It should then apply once. For `load/visit`, retry and verify the visit reward/date marker is applied once. A business rejection should be recorded as an idempotent rejected outcome; a database exception should roll the whole SQL call back and should not reserve the command request ID.

### Legacy snapshot preflight (activation only; not performed by these RPCs)

`economy_load_visit` must not import, normalize, or rewrite a legacy snapshot to decide whether to give a first-visit reward. The local migration now provides `economy_assess_legacy_profile` and `economy_activate_legacy_profile`: assessment writes only a source/candidate audit snapshot, and activation requires the exact approved source hash, candidate hash, and UTC date. Activation locks `player_state` then its control row, rechecks the source/candidate, applies only the prepared compatible candidate, and sets `server_mode` last. It does not import localStorage-only saves. This local workflow is not yet PostgreSQL-tested.

Use independent synthetic copies of these legacy snapshots and compare the dry-run result with `normalizeState()`:

| Legacy fields in stored snapshot | Expected preflight result |
|---|---|
| `upgradeLevels['second-pot'] > 0`, with no `upgrades` entry | Detect that normalization creates ownership of `second-pot`; classify as an existing player, not a first visit. Do not lose the purchase. |
| `pointsRetired !== true` with valid nonnegative `points`, or no `points` field | Preview the exact current `normalizeState()` conversion: add legacy `points` (or its `score` fallback) to `balance`, compute `score = max(saved score, lifetimeDumplings, saved balance)`, then set `points = 0` and `pointsRetired = true`. Confirm the source snapshot retains the original numbers and repeated activation cannot transfer them twice. Invalid points or an overflow must remain review-only. |
| `dailyDate` is today but `dailyTaskVariant` is absent or not the server's UTC variant | Keep the profile in manual review. Do not infer `classic`, discard current task progress, or recalculate claim status. A stale variant for a past day may be replaced only by ordinary server UTC rollover after the source day's state has passed validation. |
| `achievementClaims` is absent | Do not infer an empty claim ledger from an empty `achievements` array. A returning or ambiguous profile remains in review; only a provably fresh canonical profile can safely start with no historical achievement claims. |
| `levelClaims` is absent | Compute the same normalized score as the client: `max(score, lifetimeDumplings, balance)`. If it reaches the first claimable level threshold (500), keep the profile in review; otherwise an empty ledger is safe to initialize. Never use raw `score` alone for this decision. |
| `taskClaimedOn` is today and `taskBalanceRewardVersion` is missing or not 1 | Keep the profile in manual review. Do not apply the legacy +5 conversion during migration because the prior payout history is uncertain; do not treat the task as unclaimed. `load_visit` must not perform the conversion or pay again. |

For each ready fixture, assert activation requires the exact source hash, candidate hash, and dry-run UTC date, then commits the reviewed candidate once while switching mode last. A second activation must not replay conversions or change revision. Review-only fixtures must preserve `game_state`, balance, purchases, timers, claims, and control/revision state. Test a same-day task marker with an unresolved balance-reward version, unknown top-level data, SQL NULL state when the actual table permits it, JSON null and scalar JSONB through `economy_assess_legacy_profile` (manual-review result, no exception), legacy timer aliases without stable batch ID/slot, expired/mismatched timers, contradictory partial daily-task evidence, and current-day batch/collection evidence paired with stale daily dates.

### Daily task shape and streak claim-history compatibility

- `_pelmeni_is_first_visit()` returns `true` only when `dailyTasks` has all seven current task IDs (`login`, `cook`, `upgrade`, `collect`, `collect-dumplings`, `collect-two`, `two-pots`) and every slot contains exactly `progress` and `claimed`. A missing slot or an unknown nested property in an otherwise empty-looking state is ambiguous and must not enable first-visit treatment.
- This exact-shape requirement is applied after reliable old-player evidence is examined. A profile with confirmed prior balance, batches, a visit/claim marker, or other reliable progress may still be classified as returning when `dailyTasks` is incomplete. Preflight may fill an absent inert slot with `{progress: 0, claimed: false}` only when its related history does not imply missing activity/claim evidence. For example, missing `cook` alongside nonzero `taskBatches` or an active batch is manual review unless the current-day `taskClaimedOn` marker proves that the cook task was already claimed; in that case preflight may restore `claimed: true` and must not issue another reward. Unknown nested task properties are not interpreted or discarded: preserve the source snapshot and require manual review.
- A `streakRewardClaims` entry is accepted only in the client's `YYYY-MM-DD:<digits>:<digits>` form and only when its date is a real UTC calendar day. Preserve distinct well-formed markers, including marker suffixes the current client recognizes syntactically. Do not silently filter malformed strings or invalid dates during server activation: with `loginRewardDate` they make prior payout history ambiguous and the profile requires manual review.
- Exact duplicate valid streak markers are semantically inert: the client normalizes them with `Set`. The migration may deduplicate them in the reviewed candidate while retaining first-occurrence order; the immutable source snapshot must retain the original duplicates. This must not add or remove a claim for any distinct key and must never change balance.
- Required SQL regressions: a canonical empty state missing one task slot returns `NULL` from `_pelmeni_is_first_visit`; an empty state with an extra property inside a known slot also returns `NULL`; a returning profile with reliable prior balance and a missing inert task slot remains eligible for safe preflight completion; valid streak visit/claim markers pass validation; duplicate markers are deduplicated without payout; malformed marker syntax and an impossible calendar date fail validation and remain review-only, including when `loginRewardDate` is populated. Assert the original source JSON and balance are unchanged by assessment, and assert the candidate retains all distinct valid markers.

## 6. Atomic legacy-save guard and authorization

- As the trusted server role, RPC execution succeeds only for a profile whose control row explicitly has `server_mode = true`.
- A profile without a control row, with `server_mode = false`, or without a matching `player_state` row returns a fail-closed response and is not created or modified.
- Before enabling any real profile, test that the Edge Function passes only the Telegram ID extracted from verified `initData`, never an ID copied from the request body.
- Reproduce the current Edge `save` write exactly as `INSERT ... ON CONFLICT (telegram_id) DO UPDATE SET game_state = ..., updated_at = ...` using the trusted test role and without the transaction-local economy marker. On an inactive profile it should retain current behavior; on an enabled profile it must fail in the trigger and leave `game_state`, `updated_at`, and `revision` unchanged.
- Run two sessions concurrently: one executes a server economy RPC while the other sends the old full-state upsert for that same enabled profile. In either lock order the old write must not commit after server mode is enabled; the state must be either the serialized server result or unchanged, never the stale client snapshot. Verify the service role and trigger use the same `player_state`-then-control lock order and watch for deadlocks.
- Exercise the future mode-switch transaction with a concurrent old upsert. - The trigger prevents the current full-state upsert from overwriting server-mode rows without changing Edge Function code. The Edge Function still needs a later change to route `load`/commands through RPC and translate the trigger rejection into a deliberate client response; it is not yet a complete client cutover.

## 7. What this migration does not yet test or provide

- The local migration includes per-profile assessment and activation RPCs; it does not bulk-activate profiles or import local saves.
- The Edge Function is not changed to call `economy_load_visit` or the economy commands. Do not deploy or expose this schema as a completed client cutover.
- The local activation helper preserves unknown JSON fields, confirmed progress/purchases/claims, and exact valid future active-batch identifiers, slots, and timer values. It mirrors the client's deterministic legacy `points` retirement in the prepared candidate and retains the original source snapshot; it does not perform the uncertain legacy task-balance +5 conversion. It only rolls expired daily fields to the server UTC day. Legacy single-batch aliases without a stable batch ID/slot, elapsed or inconsistent batch timers, ambiguous same-day task/claim evidence, malformed data, and uncertain first-visit/claim histories remain `manual_review_required`; they are not rewritten or activated. `second-pot` legacy ownership is converted only by the explicit prepared candidate. The helper never imports localStorage-only saves or grants new rewards. These claims still require execution in disposable PostgreSQL.
